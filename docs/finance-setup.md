# Финансовый учёт — запуск и проверка

> ВНИМАНИЕ: внедрение выполняется вручную после проверки PR №26. 
> У финансового модуля **новые таблицы D1**, старые заказы и склад не мигрируются.

## 1. Перед Merge: подготовить D1

1. Откройте Cloudflare → Storage & databases → D1 → производственную базу магазина (ранее `five-oceans-store`).
2. Создайте резервную копию существующей D1. Не переключайте production на preview DB.
3. Откройте **Console** и примените однократно SQL из:
   `migrations/2026-10-23-finance-mvp.sql`.
4. Проверка только чтением:
   `SELECT name FROM sqlite_master WHERE type='table' AND name LIKE 'finance_%' ORDER BY name;`
   Должно быть 5 таблиц:
   `finance_products`, `finance_suppliers`, `finance_receipts`,
   `finance_supplier_payments`, `finance_expenses`.
5. **Не удаляйте** `orders`, `order_items`, `inventory`, `inventory_exclusions`.

## 2. Объединить PR и открыть финансы

1. Проверить зелёные статусы тестов GitHub и Cloudflare Pages.
2. **Merge pull request → Confirm merge** в PR №26.
3. Убедиться, что Cloudflare получил свежую Production-сборку.
4. Войти обычным способом в `/developers`, далее открыть `/finance`.
5. Файл Excel скачивается по ссылке **Скачать Excel (.xlsx)** на финансовой странице.

## 3. Кнопка Pages CMS «Передать ...»

Этот шаг выполняется **один раз**. Он необходим только для автоматической кнопки в Pages.
Пока секрет не настроен, можно безопасно пользоваться ручной кнопкой «Синхронизировать товары из Pages CMS» на `/finance`.

1. Сгенерировать уникальный случайный секрет **от 32 символов** (не использовать пароль CRM).
2. Cloudflare Pages → five-oceans-merch → Settings → Variables and Secrets → Production:
   `FINANCE_SYNC_TOKEN` = этот секрет. Сохранить и обновить production-деплой.
3. GitHub → репозиторий `five-oceans-merch` → Settings → Secrets and variables →
   Actions → New repository secret: `FINANCE_SYNC_TOKEN` = тот **же** секрет.
4. В Pages CMS для желаемого товара включить переключатель
   **«Передать в финансовый учёт»**, оставить **«Опубликовать на сайте»** выключенным.
   Сохранить Pages CMS, затем запустить действие
   **«Передать отмеченные товары в финансовый учёт»**.
5. Если Action не работает, проверить вкладку GitHub **Actions** → `Pages CMS → Financial CRM`;
   секреты не копировать в сообщения и не публиковать.

## 4. Порядок работы с новыми товарами

- **Создать карточку**: в Pages, опубликовано = **нет**.
- **Зарегистрировать в финансах**: отметить finance_enabled и синхронизировать вручную
  либо action-кнопкой. Складская позиция не создаётся.
- **Подтвердить приёмку**: после физического получения указать в `/finance`
  поставщика, цвет/размер, тип договора, количество и цену поставщика. 
  Количество на складе увеличится; товар остаётся скрыт с сайта.
- **Публикация**: если всё проверено, включить в Pages
  «Опубликовать на сайте» и «В наличии — этот цвет».
- **Продажа**: как и раньше, статус заказа «Оплачен» списывает склад.
  Финансовая сводка видит оплаченные заказы без повторного проведения.
- **Оплата поставщику**: отдельно внести реальную выплату в `/finance`.
  Для товара под реализацию долг начисляется только за проданные единицы.

## Пределы первой версии

- Учитываются **фактически полученные партии**, не предварительные заказы поставщикам;
  плановые закупки — будущий этап.
- Себестоимость по FIFO. Если в системе есть старые продажи, но их партии
  ещё не внесены, появляется предупреждение, а прибыль неполная.
- Налог 6% — **управленческая оценка** по заказам со статусом «Оплачен», 
  не расчёт налоговой декларации.
- Возвраты, скидки, агентские особенности, комиссии и точные даты денежных
  поступлений требуют отдельного внедрения.
- Записанные финансовые операции на данном этапе не удаляются через интерфейс.
  Для корректировок и сторно потребуется отдельный безопасный модуль.

## Однократный перенос девяти старых товаров по известной себестоимости (PR №29)

**Перед переносом:** сохраните точку восстановления production D1 (Cloudflare → D1 →
five-oceans-store → Time Travel). Убедитесь, что в базе уже созданы пять
таблиц первой миграции finance-mvp.sql.

1. Откройте D1 → **Console** и **один раз** выполните
   `migrations/2026-10-23-finance-opening-batches.sql`.
   Команды `ALTER TABLE finance_receipts ADD COLUMN ...` нельзя запускать дважды.
   Копируйте собственно SQL-код (без Markdown и комментариев `--`).
2. Проверка:
   `SELECT name FROM sqlite_master WHERE type='table' AND name IN ('finance_batches','finance_opening_state');`
   Должно вернуть обе таблицы.
3. После успешных GitHub и Cloudflare проверок объедините **PR №29**.
4. Войдите в `/developers` и откройте `/finance`.
5. Вверху страницы нажмите **«Перенести существующие товары и остатки (один раз)»**.
6. Обновите страницу: должны быть 9 товаров, один поставщик «Неизвестный
   поставщик», партия «Начальная партия № 1» и фактические текущие ненулевые
   остатки из D1. Если товар с нулевым остатком, он зарегистрирован финансово,
   но без фиктивной закупленной партии.
7. Проверьте цены: худи **2 950 ₽**, свитшоты **2 175 ₽**, футболки **1 400 ₽**,
   шапка «Полосатка» **700 ₽**. Эти цены закреплены за исходными product_id,
   не распространяются автоматически на будущие товары.
8. Сверьте количества в «Склад»: они не должны измениться. Долг старых партий
   по умолчанию равен нулю: исторические платежи и обязательства не придуманы.
9. Повторный перенос программно и через D1 запрещён. Если он не прошёл,
   сохраните сообщение ошибки и устраните причину — **не повторяйте вручную
   INSERT в finance_receipts**, это удвоит себестоимость.

**С этого момента** расходы, выручка и налог в финансовой сводке рассчитываются
по продажам после даты первичного переноса. Предыдущие продажи не переписываются.
Новые поступления добавляются через обычную форму финансового кабинета:
название партии одинаковое у двух разных поставщиков допустимо, потому что
ключ партии включает ID поставщика. Используйте фильтры по поставщику/партии
в таблице ниже или экспортируйте все партии в Excel.
