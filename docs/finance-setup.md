# Финансовый учёт — запуск и проверка

> ВНИМАНИЕ: внедрение выполняется вручную после проверки PR №26. 
> У финансового модуля **новые таблицы D1**, старые заказы и склад не мигрируются.

## 1. Перед Merge: подготовить D1

1. Откройте Cloudflare → Storage & databases → D1 → производственную базу магазина (ранее `five-oceans-store`).
2. Создайте резервную копию существующей D1. Не переключайте production на preview DB.
3. Откройте **Console** и примените однократно SQL из:
   `migrations/2026-10-23-finance-mvp.sql`.
4. Проверка только чтением:
   `SELECT name FROM sqlite_master WHERE type='table' AND name LIKE 'finance_%' ORDER BY name;`
   Должно быть 5 таблиц:
   `finance_products`, `finance_suppliers`, `finance_receipts`,
   `finance_supplier_payments`, `finance_expenses`.
5. **Не удаляйте** `orders`, `order_items`, `inventory`, `inventory_exclusions`.

## 2. Объединить PR и открыть финансы

1. Проверить зелёные статусы тестов GitHub и Cloudflare Pages.
2. **Merge pull request → Confirm merge** в PR №26.
3. Убедиться, что Cloudflare получил свежую Production-сборку.
4. Войти обычным способом в `/developers`, далее открыть `/finance`.
5. Файл Excel скачивается по ссылке **Скачать Excel (.xlsx)** на финансовой странице.

## 3. Кнопка Pages CMS «Передать ...»

Этот шаг выполняется **один раз**. Он необходим только для автоматической кнопки в Pages.
Пока секрет не настроен, можно безопасно пользоваться ручной кнопкой «Синхронизировать товары из Pages CMS» на `/finance`.

1. Сгенерировать уникальный случайный секрет **от 32 символов** (не использовать пароль CRM).
2. Cloudflare Pages → five-oceans-merch → Settings → Variables and Secrets → Production:
   `FINANCE_SYNC_TOKEN` = этот секрет. Сохранить и обновить production-деплой.
3. GitHub → репозиторий `five-oceans-merch` → Settings → Secrets and variables →
   Actions → New repository secret: `FINANCE_SYNC_TOKEN` = тот **же** секрет.
4. В Pages CMS для желаемого товара включить переключатель
   **«Передать в финансовый учёт»**, оставить **«Опубликовать на сайте»** выключенным.
   Сохранить Pages CMS, затем запустить действие
   **«Передать отмеченные товары в финансовый учёт»**.
5. Если Action не работает, проверить вкладку GitHub **Actions** → `Pages CMS → Financial CRM`;
   секреты не копировать в сообщения и не публиковать.

## 4. Порядок работы с новыми товарами

- **Создать карточку**: в Pages, опубликовано = **нет**.
- **Зарегистрировать в финансах**: отметить finance_enabled и синхронизировать вручную
  либо action-кнопкой. Складская позиция не создаётся.
- **Подтвердить приёмку**: после физического получения указать в `/finance`
  поставщика, цвет/размер, тип договора, количество и цену поставщика. 
  Количество на складе увеличится; товар остаётся скрыт с сайта.
- **Публикация**: если всё проверено, включить в Pages
  «Опубликовать на сайте» и «В наличии — этот цвет».
- **Продажа**: как и раньше, статус заказа «Оплачен» списывает склад.
  Финансовая сводка видит оплаченные заказы без повторного проведения.
- **Оплата поставщику**: отдельно внести реальную выплату в `/finance`.
  Для товара под реализацию долг начисляется только за проданные единицы.

## Пределы первой версии

- Учитываются **фактически полученные партии**, не предварительные заказы поставщикам;
  плановые закупки — будущий этап.
- Себестоимость по FIFO. Если в системе есть старые продажи, но их партии
  ещё не внесены, появляется предупреждение, а прибыль неполная.
- Налог 6% — **управленческая оценка** по заказам со статусом «Оплачен», 
  не расчёт налоговой декларации.
- Возвраты, скидки, агентские особенности, комиссии и точные даты денежных
  поступлений требуют отдельного внедрения.
- Записанные финансовые операции на данном этапе не удаляются через интерфейс.
  Для корректировок и сторно потребуется отдельный безопасный модуль.

## Однократный перенос девяти старых товаров по известной себестоимости (PR №29)

**Перед переносом:** сохраните точку восстановления production D1 (Cloudflare → D1 →
five-oceans-store → Time Travel). Убедитесь, что в базе уже созданы пять
таблиц первой миграции finance-mvp.sql.

1. Откройте D1 → **Console** и **один раз** выполните
   `migrations/2026-10-23-finance-opening-batches.sql`.
   Команды `ALTER TABLE finance_receipts ADD COLUMN ...` нельзя запускать дважды.
   Копируйте собственно SQL-код (без Markdown и комментариев `--`).
2. Проверка:
   `SELECT name FROM sqlite_master WHERE type='table' AND name IN ('finance_batches','finance_opening_state');`
   Должно вернуть обе таблицы.
3. После успешных GitHub и Cloudflare проверок объедините **PR №29**.
4. Войдите в `/developers` и откройте `/finance`.
5. Вверху страницы нажмите **«Перенести существующие товары и остатки (один раз)»**.
6. Обновите страницу: должны быть 9 товаров, один поставщик «Неизвестный
   поставщик», партия «Начальная партия № 1» и фактические текущие ненулевые
   остатки из D1. Если товар с нулевым остатком, он зарегистрирован финансово,
   но без фиктивной закупленной партии.
7. Проверьте цены: худи **2 950 ₽**, свитшоты **2 175 ₽**, футболки **1 400 ₽**,
   шапка «Полосатка» **700 ₽**. Эти цены закреплены за исходными product_id,
   не распространяются автоматически на будущие товары.
8. Сверьте количества в «Склад»: они не должны измениться. Долг старых партий
   по умолчанию равен нулю: исторические платежи и обязательства не придуманы.
9. Повторный перенос программно и через D1 запрещён. Если он не прошёл,
   сохраните сообщение ошибки и устраните причину — **не повторяйте вручную
   INSERT в finance_receipts**, это удвоит себестоимость.

**С этого момента** расходы, выручка и налог в финансовой сводке рассчитываются
по продажам после даты первичного переноса. Предыдущие продажи не переписываются.
Новые поступления добавляются через обычную форму финансового кабинета:
название партии одинаковое у двух разных поставщиков допустимо, потому что
ключ партии включает ID поставщика. Используйте фильтры по поставщику/партии
в таблице ниже или экспортируйте все партии в Excel.


## Быстрое поступление: товары и поставщики (PR № 31)

В секции **«Добавить операцию → Поступление на склад»** используются два способа
выбора товара и поставщика: выпадающий полный список и поле ввода с подсказками
по ключевым словам, включая набор латиницей (например, `ne kak` находит
«Не как все»). Для точной складской записи **товар должен быть выбран из
реального каталога Pages, уже зарегистрированного в финансовой базе**.
Произвольный новый товар через это поле создавать нельзя: сначала Pages,
затем синхронизация финансового учёта. Это защищает от дублирования SKU.

**Старые девять товаров** теперь доступны в приёмке независимо от текущего
значения `finance_enabled` в Pages, поскольку уже есть в `finance_products`.
Любой новый товар, отмеченный для финансового учёта, появится после
синхронизации из Pages.

**Поставщик** выбирается из списка либо вписывается в поле; незнакомое системе
название автоматически регистрируется **в той же транзакции**, что партия,
финансовое поступление и увеличение складского остатка. Отдельная форма
добавления поставщика убрана, ранее введённые имена остаются. Названия партий
у разных поставщиков могут совпадать — внутренние ID партий отличаются.
Для новых товаров и старых пополнений процесс одинаковый.

**После деплоя:** открыть `/finance` и обновить через Ctrl+F5. Попробовать
написать `ne kak` в поле поиска товара и выбрать подходящий цвет/размер из
предложений. Поставщика можно набрать вручную. До реального поступления не
подтверждать приёмку с вымышленным количеством.

В этой доработке **нет SQL-миграции**, ранее записанные остатки и партии
не корректируются. Не требуется запускать начальный перенос ещё раз.


## Единая операция: поступление + оплата + расходы (PR № 32)

В `/finance` блок «Добавить операцию» теперь представляет собой **одну форму с
одной кнопкой «Подтвердить операцию»**.

**Обычно:** режим «Новое поступление». Заполните товар/цвет/размер,
поставщика, партию, тип договора, количество и себестоимость. Сумма платежа
поставщику и сопутствующие расходы необязательны. Кнопка «+ Ещё расход»
позволяет добавить до 10 отдельных расходов с назначениями и суммами.

Одно нажатие вызывает **один атомарный Cloudflare D1 `batch()`**:
создание поставщика при необходимости, создание/поиск партии, фиксация
поступления, необязательная выплата по **только что вставленному receipt.id**,
необязательные расходы и увеличение склада. При ошибке любой SQL-операции
откатывается весь набор, включая складские остатки. Вводим только фактически
совершённые платежи/расходы; пустые поля не сохраняются как нули.

**Позднее:** в том же едином поле «Что оформляем?» выбрать
«Доплата / отдельный расход без нового поступления». В этом режиме складские
поля скрыты, при выплате выбирается уже зарегистрированная партия, расход
можно записать без выплаты и выбора партии. Единственная кнопка та же,
склад не меняется.

Интерфейс блокирует повторное нажатие кнопки во время отправки; после
успешной операции происходит перенаправление на `/finance` с уведомлением.
Для нового режима не нужна SQL-миграция. Старые денежные и складские записи
не редактируются.

**Важно:** `last_insert_rowid()` используется сразу после INSERT в
`finance_receipts` и до любого другого INSERT; этот идентификатор
привязывает платёж к конкретному поступлению, даже если одинаковые
номера партии используются несколькими поставщиками.


## Снятие тестового товара с сайта и очистка базы

Карточка **«ТЕСТ CRM — удалить после проверки»** имеет точную пару
`product_id=b3ec1243-b170-4d8c-94b6-2a7feef4b9fe`,
`slug=test_crm`. Она удалена из `data/products.json`; девять остальных
товаров остаются без изменений. В интерфейсе вкладки «Склад» убрана кнопка
ручной синхронизации: новые позиции появляются после финансового поступления.
Сам механизм синхронизации оставлен как служебный, для диагностики и миграций,
и не вызывается при обычной приёмке.

**После Merge и успешного production deployment** открыть закрытый `/finance`
и найти блок «Завершить проверку: удалить ТЕСТ CRM». Он показывает найденные
записи склада, финансов, платежей и тестовые заказы; ссылка скачивает JSON
с содержащимися в D1 тестовыми записями. **Сначала** нужно сохранить эту
копию и проверить доступность контрольной точки восстановления Cloudflare
D1 Time Travel. После проверки ввести точную фразу
`УДАЛИТЬ ТЕСТ CRM`, поставить флажок о копии и подтвердить удаление.

Очистка разрешена **только** по жёстко заданному UUID + slug. Блокируются
активные резервы и заказы, где есть другие товары. SQL удаления заказов,
оплат, партий, товара, складских строк и исключений проводится **атомарно**
через один `db.batch()`. Поставщики удаляются, лишь когда остаются без
партийных поступлений **и в их имени есть слово «тест»**; партии — только
если не используются другим товаром.

**Важное ограничение:** таблица `finance_expenses` не хранит ссылок на
товар или партию. Без надёжных идентификаторов автоматически удалять
записанные общие расходы нельзя — возможно, понадобится отдельная
точечная проверка тестовых расходов. Резервная копия JSON также не является
резервной копией всей D1; общесистемное восстановление выполняется через
Cloudflare Time Travel.

После выполнения блока очистки финансового товара больше не будет,
повторная операция блокируется. После успешной очистки временную кнопку
рекомендуется удалить отдельным PR — она больше не нужна.


## Передача в финансовый учёт по отдельным цветам (2026-10-24)

**Теперь переключатель «Передать в финансовый учёт — этот цвет» находится
внутри каждой группы «Цвета товара» Pages CMS**, рядом с «В наличии»,
«Наш выбор» и «Новинка». Общего переключателя у всей модели больше нет.

- Все ранее заведённые и перенесённые 9 товаров / 11 цветовых вариантов
  сохранены: финансовая отметка для них включена при переносе структуры.
  Это касается и только что добавленного **тёмно-синего** цвета
  футболки «Не как все» (код `navy`, размер `44-46`, цена **1 900 ₽**).
- Новые цвета Pages CMS создаются с **выключенной** финансовой отметкой.
- Чтобы принять новый цвет уже зарегистрированной модели: в Pages открыть
  модель, развернуть новый цвет, включить финансовую отметку и сохранить
  изменения. После публикации Pages цвет появится в выпадающем списке
  «Поступление на склад» при следующем открытии `/finance`. Синхронизация
  всей модели повторно **не требуется**, если она уже есть в финучёте.
- Если это **совершенно новая модель**, достаточно отметить хотя бы один
  её цвет и нажать «Синхронизировать товары из Pages CMS» на `/finance`,
  либо использовать штатную Pages CMS action. После регистрации модели
  в финансовой базе в приёмке показываются **только отмеченные цвета**.
- Финансовые поступления продолжают фиксироваться по SKU
  `v:<code цвета>|<размер>`. Отметка сама по себе не создаёт складского
  количества, не удаляет ранее оформленные партии и не влияет на продажи
  и финансовый отчёт. При снятии отметки скрывается только возможность
  **новой** приёмки по этому цвету; история остаётся.
- Изменения затрагивают только Pages CMS, фильтрацию поступлений и
  регистрацию финансового товара. **Новых SQL-миграций нет**: таблица
  `finance_products` по-прежнему хранит общую модель, а цвет указывается
  при приёмке отдельным SKU.

**Важно:** дождитесь слияния PR с этим изменением, прежде чем вручную
переключать новый параметр в Pages CMS: до Merge в редакторе нового поля нет.
